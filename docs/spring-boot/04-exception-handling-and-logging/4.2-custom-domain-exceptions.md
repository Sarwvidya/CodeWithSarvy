# 4.2 Custom Domain Exceptions

[← Back to Chapter 4: Exception Handling, Logging & Production Support](./index.md)

Domain-driven design emphasizes creating domain-specific exceptions to model business rule violations explicitly, rather than overloading generic Java exceptions (`RuntimeException` or `IllegalArgumentException`).

---

## 1. Clean Domain Exception Hierarchy

Always base business domain exceptions on unchecked exceptions (`RuntimeException`) so that service signatures remain clean and transactional rollback occurs automatically:

```
                    ┌────────────────────────┐
                    │    RuntimeException    │
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │  BaseBusinessException │
                    └───────────┬────────────┘
         ┌──────────────────────┼──────────────────────┐
         │                      │                      │
┌────────▼───────────┐ ┌────────▼───────────┐ ┌────────▼───────────┐
│ ResourceNotFound   │ │ ConflictException  │ │ InsufficientBalance│
│ Exception (404)    │ │ (Duplicate) (409)  │ │ Exception (422)    │
└────────────────────┘ └────────────────────┘ └────────────────────┘
```

---

## 2. Designing the Base Exception Class

```java
public abstract class BaseBusinessException extends RuntimeException {

    private final String errorCode;
    private final Instant timestamp;

    protected BaseBusinessException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
        this.timestamp = Instant.now();
    }

    protected BaseBusinessException(String errorCode, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
        this.timestamp = Instant.now();
    }

    public String getErrorCode() { return errorCode; }
    public Instant getTimestamp() { return timestamp; }
}
```

### Specialized Concrete Exceptions
```java
public class ResourceNotFoundException extends BaseBusinessException {
    public ResourceNotFoundException(String resourceName, Object identifier) {
        super("RESOURCE_NOT_FOUND", "%s with identifier [%s] was not found".formatted(resourceName, identifier));
    }
}

public class DuplicateResourceException extends BaseBusinessException {
    public DuplicateResourceException(String resourceName, String field, Object value) {
        super("DUPLICATE_RESOURCE", "%s already exists with %s: [%s]".formatted(resourceName, field, value));
    }
}
```

## 3. Best Practices & Anti-Patterns

| Recommended Best Practice | Anti-Pattern to Avoid |
| :--- | :--- |
| Use unchecked exceptions (`RuntimeException`) so `@Transactional` automatically triggers rollback. | Using checked exceptions that require throwing in every method signature. |
| Provide structured context (e.g., entity name, ID). | Throwing raw `new RuntimeException("Not found")`. |
| Centralize mapping in `@RestControllerAdvice`. | Catching exceptions in each individual controller method. |
| Use `@ResponseStatus` directly on the exception class for simple APIs. | Cluttering business classes with HTTP status codes. |
