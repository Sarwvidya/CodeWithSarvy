# 2.2 Dependency Injection & Wiring

[← Back to Chapter 2: Spring Beans & Dependency Injection](./index.md)

Dependency Injection (DI) is the concrete implementation of Inversion of Control in Spring. Objects receive their dependencies from the framework rather than creating them directly.

---

## 1. The Three Forms of Injection

Spring supports three primary mechanisms to inject collaborating dependencies into a bean:

### A. Constructor Injection (Industry Best Practice)
```java
@Service
public class UserService {
    private final UserRepository userRepository;
    private final NotificationService notificationService;

    // @Autowired is optional in Spring 4.3+ when there is only one constructor
    public UserService(UserRepository userRepository, NotificationService notificationService) {
        this.userRepository = userRepository;
        this.notificationService = notificationService;
    }
}
```

### B. Setter Injection (For Optional Dependencies)
```java
@Service
public class ReportService {
    private Formatter formatter;

    @Autowired
    public void setFormatter(Formatter formatter) {
        this.formatter = formatter;
    }
}
```

### C. Field Injection (Discouraged / Anti-Pattern)
```java
@Service
public class BadService {
    @Autowired // Avoid!
    private PaymentClient paymentClient;
}
```

---

## 2. Why Field Injection is an Anti-Pattern

Despite being compact, field injection introduces critical architectural problems:

1. **Breaks Immutability**: Fields cannot be declared `final`, making the class prone to unwanted state modification.
2. **Hides Coupling & SRP Violations**: With constructor injection, a constructor with 8 parameters immediately signals a violation of the Single Responsibility Principle. Field injection hides this smell.
3. **Hard to Unit Test**: Fields cannot be populated in pure unit tests (`new BadService()`) without using reflection or heavy Spring testing contexts.
4. **Obscures Circular Dependencies**: Field-injected classes may hide circular dependencies that surface only at runtime under specific invocation orders.

---

## 3. Circular Dependencies & Resolution

A circular dependency occurs when `Bean A` requires `Bean B`, and `Bean B` directly or indirectly requires `Bean A`:

```
┌────────┐               ┌────────┐
│ Bean A ├──────────────>│ Bean B │
└────────┘               └────────┘
    ▲                        │
    └────────────────────────┘
```

### What Happens in Spring Boot?
Starting in **Spring Boot 2.6+**, circular dependencies are **forbidden by default** and result in immediate startup failure (`BeanCurrentlyInCreationException`).

### Production Fixes:
1. **Refactor Architecture (Recommended)**: Extract shared logic into a distinct third component (`Bean C`) that both `A` and `B` consume.
2. **Event-Driven Decoupling**: Replace direct synchronous method invocation with Spring `ApplicationEventPublisher`.
3. **`@Lazy` Injection (Workaround)**: Break the initialization cycle by having Spring inject a lazy proxy that initializes on first method call:
   ```java
   public UserService(@Lazy AuditService auditService) {
       this.auditService = auditService;
   }
   ```
