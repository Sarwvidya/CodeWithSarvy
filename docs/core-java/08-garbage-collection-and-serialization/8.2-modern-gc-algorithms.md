# 8.2 Modern GC Collectors: Serial, Parallel, G1 GC, and ZGC

[← Back to Chapter 8: Garbage Collection & Serialization](./index.md)

Selecting the right GC collector depends on application priorities: throughput, pause latency, or memory footprint.

---

## 1. Evolution of HotSpot GC Collectors

| Collector | JVM Flag | Target Workload | STW Pause Duration |
| :--- | :--- | :--- | :--- |
| **Serial GC** | `-XX:+UseSerialGC` | Single-core micro-containers | High (Single-threaded STW) |
| **Parallel GC** | `-XX:+UseParallelGC` | Batch processing, high throughput | Medium-High (Multi-threaded STW) |
| **G1 GC (Default)** | `-XX:+UseG1GC` | General enterprise web apps | Low (Configurable, e.g. 200ms) |
| **ZGC** | `-XX:+UseZGC` | Ultra-low latency enterprise APIs | Sub-millisecond (&lt; 1 ms) |
| **Shenandoah** | `-XX:+UseShenandoahGC` | Ultra-low latency concurrent | Sub-millisecond (&lt; 1 ms) |

---

## 2. G1 GC: Region-Based Memory Partitioning

- Partitions the heap into thousands of equal-sized **Regions** (1 MB to 32 MB).
- Regions are dynamically assigned roles (Eden, Survivor, Old, Humongous).
- Tracks how much garbage each region contains and prioritizes collecting regions with the **most garbage first** ("Garbage-First").
- Soft pause goal: `-XX:MaxGCPauseMillis=200` (defaults to 200 milliseconds).

---

## 3. ZGC: Ultra-Low Latency Scalable Collector

- Performs almost all heavy GC phases (marking, relocation, pointer remapping) **concurrently** while user request threads run.
- Utilizes **Colored Pointers** (reference bit metadata) and **Load Barriers** to intercept object dereferencing during live relocation.
- Pause times consistently stay below 1 millisecond regardless of whether heap size is 16 MB or 16 TB.
