# 3.2 String vs StringBuilder vs StringBuffer

[← Back to Chapter 3: Strings in Java](./index.md)

When manipulating text in performance-critical loops, choosing the correct String abstraction prevents massive Heap memory churn and GC pressure.

---

## 1. Feature Comparison Matrix

| Feature | `String` | `StringBuilder` | `StringBuffer` |
| :--- | :--- | :--- | :--- |
| **Mutability** | **Immutable** (new instance on change) | **Mutable** (modifies internal buffer) | **Mutable** (modifies internal buffer) |
| **Thread Safety** | **Yes** (Inherently thread-safe) | **No** (Unsynchronized) | **Yes** (`synchronized` methods) |
| **Performance** | Slow for repeated concatenation | **Fastest** (Zero lock overhead) | Slower due to synchronization locks |
| **Introduced** | Java 1.0 | Java 5 | Java 1.0 |
| **Primary Use Case** | Constants, DTOs, Maps, APIs | Local text assembly, loops | Multithreaded shared string building |

---

## 2. The String Concatenation Anti-Pattern in Loops

```java
// SEVERE PERFORMANCE ANTI-PATTERN: O(N²) time & millions of orphaned Heap objects!
String result = "";
for (int i = 0; i < 10_000; i++) {
    result += i; // Allocates a NEW String on EVERY single iteration!
}

// OPTIMAL PRODUCTION PATTERN: O(N) time & single mutable buffer allocation!
StringBuilder sb = new StringBuilder(50_000); // Pre-allocate estimated capacity
for (int i = 0; i < 10_000; i++) {
    sb.append(i);
}
String finalOutput = sb.toString();
```

:::info Modern Compiler Optimization Note
For simple single-statement expressions (`String msg = "User: " + name + " Id: " + id;`), the Java compiler (Java 9+ via `invokedynamic` / `StringConcatFactory`) automatically optimizes concatenation. However, **inside loops**, manual use of `StringBuilder` remains mandatory.
:::
