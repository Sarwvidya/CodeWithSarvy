# 7.2 Modern Garbage Collectors: G1 to ZGC

[← Back to Chapter 7: Garbage Collection & Serialization](./index.md)

Selecting the proper Garbage Collector configuration directly dictates application throughput, latency, and pause predictability.

---

## 1. Evolution of HotSpot Garbage Collectors

| Collector | JVM Flag | Target Workload | Max Pause Time | Heap Scaling |
| :--- | :--- | :--- | :--- | :--- |
| **Serial GC** | `-XX:+UseSerialGC` | Single-core, small memory (&lt; 100MB), embedded | Seconds (Stop-The-World) | Small (&lt; 512MB) |
| **Parallel GC** | `-XX:+UseParallelGC` | Batch processing, high CPU throughput | Hundreds of milliseconds | Medium (1–4GB) |
| **G1 GC** *(Default)* | `-XX:+UseG1GC` | General enterprise server workloads | Predictable (~100–200ms) | Large (4–64GB) |
| **ZGC** (Generational) | `-XX:+UseZGC` | Ultra-low latency, mission-critical microservices | **Sub-millisecond (&lt; 1ms)** | Gigabytes to **16 Terabytes!** |

---

## 2. G1 GC (Garbage-First Collector)
Default since Java 9. Divides the heap into equal-sized virtual **Regions** (1MB to 32MB):
- Regions are dynamically assigned roles: Eden, Survivor, Old, or Humongous.
- G1 prioritizes collecting regions containing the highest ratio of dead objects ("Garbage-First").
- Allows developers to set soft pause-time goals: `-XX:MaxGCPauseMillis=200`.

---

## 3. ZGC (Z Garbage Collector - Ultra-Low Latency)

ZGC (stabilized in Java 15, Generational in Java 21) achieves sub-millisecond pause times regardless of heap size:
- **Concurrent Execution**: Performs Mark, Relocate, and Compact phases concurrently with application worker threads.
- **Colored Pointers**: Uses metadata bits within 64-bit object reference pointers to track GC state.
- **Load Barriers**: Intercepts thread reference reads; if an object was relocated by GC, the load barrier repairs the pointer on the fly without stopping the thread!
