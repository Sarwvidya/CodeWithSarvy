# 4.5 Custom Exceptions & Enterprise Best Practices

[← Back to Chapter 4: Exception Handling](./index.md)

In production enterprise architectures, standard library exceptions like `IllegalArgumentException` are often too generic to communicate specific business-domain failures.

---

## 1. Crafting Domain-Specific Custom Exceptions

Always extend `RuntimeException` for modern business validation failures:

```java
public class ResourceNotFoundException extends RuntimeException {
    private final String resourceName;
    private final String fieldName;
    private final Object fieldValue;

    public ResourceNotFoundException(String resourceName, String fieldName, Object fieldValue) {
        super(String.format("%s not found with %s : '%s'", resourceName, fieldName, fieldValue));
        this.resourceName = resourceName;
        this.fieldName = fieldName;
        this.fieldValue = fieldValue;
    }

    public String getResourceName() { return resourceName; }
    public String getFieldName() { return fieldName; }
    public Object getFieldValue() { return fieldValue; }
}
```

---

## 2. Exception Chaining: Preserving Root Causes

When translating low-level exceptions into high-level domain exceptions, **always pass the original cause**:

```java
try {
    paymentGatewayClient.charge(req);
} catch (IOException e) {
    // PRESERVE ROOT CAUSE: Pass 'e' to constructor
    throw new PaymentProcessingException("Gateway network timeout", e);
}
```

---

## 3. Top 5 Enterprise Exception Best Practices

1. **Never Swallow Exceptions Silently**:
   ```java
   // SEVERE ANTI-PATTERN: Completely destroys system observability!
   try { ... } catch (Exception e) {}
   ```
2. **Log OR Rethrow, Never Both**: Logging at every layer creates noisy, duplicate multi-page stack traces for a single failure. Log once at the system boundary (e.g. `@RestControllerAdvice`).
3. **Use Specific Exception Types**: Don't catch generic `Exception` when you can catch `NumberFormatException`.
4. **Include Diagnostic Context**: Include failed entity IDs, requested URLs, or parameter values in the error message.
5. **Clean up Resources Deterministically**: Always utilize Try-with-Resources.
